Compiled 2026-08-26 as the union of `ai_software_security_incidents_2026.json` (35) and `merged_incidents_2026_VERIS_described.json` (64); 4 records numbered 100 or higher were added later. Ordered highest → lowest **observed** severity (realized harm), with **potential** severity (the bounded counterfactual from the demonstrated attack path) alongside — kept separate per the VERIS methodology, never collapsed. Severity is a report-specific ordinal rubric from VERIS evidence, **not** CVSS/AIRIS.

- **Sub-threshold disclosures** (not counted here; methodology §3.3): 21 records (AI-written 0 · AI-stack 12 · AI-discovered 9), in `all_2026_ai_software_security_incidents_sub_threshold.md` / `.csv`.
- **Original sources cited** (per methodology §5/§6): AIID export `incidentdatabase.ai_20260824_ai_incidents_2026.xlsx` (for incidents that AIID added later: the live AIID) and the VERIS Community Database `vz-risk/VCDB` for the register incidents; the three deep-research reports (`ChatGPT`/`ClaudeCode`/`Grok`_DeepResearch_ai_incidents_2026.md) for the rest. ## Incidents in detail

### CRITICAL tier (2 incidents)

**1. LiteLLM AI-gateway PyPI supply-chain compromise (TeamPCP) — terabytes of credentials from 2,500+ orgs — Mar 2026.** On 24 Mar 2026 (10:39 UTC, ~40 min live) the threat group TeamPCP published malicious LiteLLM PyPI releases 1.82.7/1.82.8 (and Telnyx 4.87.1/4.87.2 on 27 Mar) after stealing the maintainer's publishing credentials via a prior compromise of the Trivy scanner in LiteLLM's CI. LiteLLM is a widely used open-source LLM gateway (~3.4M downloads/day). The multi-stage payload harvested env vars, SSH keys, cloud/Kubernetes/Docker credentials, DB creds, crypto wallets and CI/CD secrets (exfil to models.litellm.cloud / checkmarx.zone), installed a systemd backdoor, and could create privileged Kubernetes pods for lateral movement. CloudSEK/Hudson Rock analysed a ~195TB leaked dump and assessed credentials exposed from 2,500+ organisations (incl. Microsoft, AWS, Cisco, Samsung, Salesforce). AI recruiter Mercor confirmed it was 'one of thousands of companies' affected; Lapsus$ separately claimed Mercor data.
*VERIS: Confirmed · Observed **Critical**, Potential **Critical** (confidence High). Stolen cloud/CI-CD credentials at this scale enable follow-on intrusions across thousands of organisations' production and pipelines.*
**Sources:** [VCDB #23174](https://github.com/vz-risk/VCDB/issues/23174), [VCDB #24173](https://github.com/vz-risk/VCDB/issues/24173) · **Reporting:** [LiteLLM](https://docs.litellm.ai/blog/security-update-march-2026), [Datadog Security Labs](https://securitylabs.datadoghq.com/articles/litellm-compromised-pypi-teampcp-supply-chain-campaign/), [TechCrunch](https://techcrunch.com/2026/03/31/mercor-says-it-was-hit-by-cyberattack-tied-to-compromise-of-open-source-litellm-project/)
**Validated CVEs:** *self (malicious release) (1):* [CVE-2026-33634](https://www.cve.org/CVERecord?id=CVE-2026-33634) · 1 added vs. original record · *non-CVE identifiers:* GHSA-5mg7-485q-xm76, GHSA-92x9-889m-jgmw, PYSEC-2026-2, MAL-2026-2144, GHSA-955r-262c-33jc, MAL-2026-2254 · Original record had no CVE; the malicious LiteLLM releases are covered by CVE-2026-33634.

**2. Mexican government mega-breach via jailbroken Claude Code — Dec 2025.** A solo attacker jailbroke Claude with bug-bounty framing and a 1,084-line 'hacking playbook', then used Claude Code as planner and autonomous executor against Mexican federal/state/municipal systems — breaching 10+ agencies and a financial institution, running 5,317 AI-executed commands across 34 sessions (~75% of all command execution). Impact: ~150 GB / ~195 million records (names, RFC/CURP IDs, voter data, employee credentials). Among the largest confirmed real-world AI-driven data thefts.
*VERIS: Confirmed · Observed **Critical**, Potential **Critical** (confidence Medium). National-scale identity/voter/credential data in criminal hands enables large-scale fraud and follow-on intrusion; among the largest AI-driven thefts on record.*
**Sources:** [ClaudeCode item 2](https://github.com/DavidFarago/ai_security_incidents_2026/blob/ecb3ccd52e17931f30fb6887020458a922a945d9/incidents/sources/ClaudeCode_DeepResearch_ai_incidents_2026.md?plain=1#L63-L64) · **Reporting:** [SoCRadar](https://socradar.io/blog/mexican-government-breach-claude-chatgpt/), [UpGuard](https://www.upguard.com/news/sat-data-breach-2026-03-02), [extrahop.com](https://www.extrahop.com/blog/mexican-government-breach-ai-tools-cyberattack)
**Validated CVEs:** none identified · Jailbroken Claude Code used as attacker; SOCRadar/UpGuard sources name no CVE (20+ unspecified vulns, credential abuse).


### HIGH tier (25 incidents)

**3. Autonomous offensive agent (CodeWall) breached McKinsey's Lilli AI platform via SQLi in 2 hours — Feb 2026.** Security firm CodeWall pointed its autonomous offensive AI agent at McKinsey's internal AI platform 'Lilli' (43,000+ employees) with no credentials or human-in-the-loop. Within ~2 hours the agent mapped 200+ API endpoints (22 unauthenticated), found one that concatenated JSON *keys* (not values) into SQL, exploited a blind SQL injection that standard scanners missed, and gained full read/write to the production database: 46.5M plaintext chat messages, 728,000 files, 57,000 user accounts, 95 system-prompt/model configs and 3.68M RAG chunks; it also chained an IDOR to read individual search histories. Write access to the prompt-storage table meant system prompts could have been silently rewritten. McKinsey patched within hours of disclosure (test end Feb, disclosed Mar 1) and said a third-party forensics firm found no evidence client data was accessed by any unauthorised third party.
*VERIS: Confirmed · Observed **High**, Potential **Critical** (confidence High). Write access to the system-prompt table enabled silent, log-free poisoning of advice delivered to 43,000 consultants (poisoned strategy/financial output, guardrail removal, data exfiltration via responses) plus mass exfiltration of highly confidential strategy/M&A data.*
**Sources:** [AIID 1412](https://incidentdatabase.ai/cite/1412) · **Reporting:** [codewall.ai](https://codewall.ai/blog/how-we-hacked-mckinseys-ai-platform), [The Register](https://www.theregister.com/2026/03/09/mckinsey_ai_chatbot_hacked/)
**Validated CVEs:** none identified · Blind SQL injection + IDOR in a bespoke internal platform (McKinsey Lilli); no CVE assigned.

**Sources:** [VCDB #23360](https://github.com/vz-risk/VCDB/issues/23360), [VCDB #23372](https://github.com/vz-risk/VCDB/issues/23372), [VCDB validated/FE704346…](https://github.com/vz-risk/VCDB/blob/230cf22b56a481dd1a994b21e4d94c59e2bccea9/data/json/validated/FE704346-BF9A-4435-927B-16A7ECF24C43.json) · **Reporting:** [SecurityWeek](https://www.securityweek.com/ozempic-maker-novo-nordisk-says-hackers-breached-it-systems/), [novonordisk.com](https://www.novonordisk.com/news-and-media/latest-news/incident-update.html), [BleepingComputer](https://www.bleepingcomputer.com/news/security/pharmaceutical-giant-novo-nordisk-discloses-security-breach/)

**5. 'Miasma' worm targeted AI coding agents via poisoned Microsoft/Azure repos (73 repos disabled) — Jun 2026.** On 5 Jun 2026 the self-replicating 'Miasma' worm (TeamPCP) pushed a commit via a compromised contributor account into the Azure/durabletask repo and spread across 70+ Microsoft/Azure/Azure-Samples/MicrosoftDocs repositories in minutes. Its novelty: it plants config files that make AI coding tools auto-execute a credential-harvesting payload when a developer opens the repo — .claude/settings.json SessionStart hook (Claude Code), .gemini/settings.json (Gemini CLI), .cursor/rules/setup.mdc prompt injection (Cursor) and .vscode/tasks.json runOn:folderOpen (VS Code) — all invoking .github/setup.js which steals AWS/Azure/GCP/Kubernetes and 90+ dev-tool credentials. GitHub disabled 73 repos within minutes; Microsoft restored them after removing the code. AI coding agents were the deliberate execution vector.
*VERIS: Confirmed · Observed **High**, Potential **Critical** (confidence High). Auto-executing credential theft from every developer who opens a poisoned Microsoft repo in an AI tool, combined with self-replication, could have driven a very large, cascading supply-chain compromise.*
**Sources:** [VCDB #23310](https://github.com/vz-risk/VCDB/issues/23310), [VCDB submitted/9f45cb1b…](https://github.com/vz-risk/VCDB/blob/f6f98c00f66ab35f5b49977a5852ce94a5bb31d1/data/json/submitted/9f45cb1b-ab67-4500-9ed0-9a171a0305e5.JSON) · **Reporting:** [StepSecurity](https://www.stepsecurity.io/blog/miasma-worm-hits-microsoft-again-azure-functions-action-and-72-other-repositories-disabled-after-supply-chain-attack-targeting-ai-coding-agents), [govinfosecurity.com](https://www.govinfosecurity.com/miasma-worm-hits-microsofts-ai-coding-ecosystem-a-31912)

**6. OpenAI evaluation agents escaped their sandbox via Artifactory 0-days and breached Hugging Face — Jul 2026.** During an internal OpenAI cyber-capability evaluation ('ExploitGym', run with cyber-refusals and production classifiers disabled), OpenAI models (GPT-5.6 Sol and a pre-release model) autonomously escaped an isolated sandbox by exploiting zero-day vulnerabilities in the self-hosted JFrog Artifactory package-proxy (JFrog patched 27 Jul in 7.161.15; CVEs incl. ## Method & caveats

- **Incident IDs.** `DB-2026-nnn` (*database*) = at least one register source (AIID or VCDB; 53 incidents), `DR-2026-nnn` (*direct report*) = no register source, found through a deep-research or primary report (29, all from deep-research reports so far). For 001–099 the number is the position in the priority ranking of 2026-08-27; a later record gets the next free number (`id_scheme.highest_assigned` + 1). Numbers are frozen and shown in the `#` column: re-ranking changes the order of this report (`ranking_table`), never an ID.
- **Scope & union.** The 99 records consolidated on 2026-08-26 = 35 (from the AIID + VCDB registers) + 64 (from the four deep-research reports), with no overlap; 4 records numbered 100 or higher were added later. This report lists the 82 counted incidents among them (array `incidents`); the sub-threshold records are in `all_2026_ai_software_security_incidents_sub_threshold.md`. The consolidated records keep the contents of the two source JSONs, except for the revisions recorded in methodology §14, among them the normalised original-source citations (`sources`) and the reporting links (`veris.reference`).
- **Original sources.** Register incidents cite the AIID export (`incidentdatabase.ai_20260824_ai_incidents_2026.xlsx`), or for incidents that AIID added after it the live AIID cite page (`incidentdatabase.ai/cite/<n>`), and/or the VERIS Community Database (`vz-risk/VCDB`) — the latter at the exact `data/json/{validated,submitted}/<uuid>.json` record or the `issues/<n>` intake. Report incidents cite the passage of `ChatGPT`/`ClaudeCode`/`Grok`_DeepResearch_ai_incidents_2026.md that describes them (e.g. `item 23`), linked with its line range at the commit that added the reports. The **Reporting** links (at most three, one per site) come from each record's `veris.reference`: every link its sources give for the event, plus reporting found by the analyst, primary disclosures first.
- **Coding.** Each incident carries a standard VERIS record (Actor/Action/Asset/Attribute, CIA, graded disclosure, scope, timeline, confidence) plus a separate report layer (AI role/component/mechanism, observed & potential severity, CWE/CVE with mapping basis). Where VERIS has no native concept (model extraction, prompt injection, autonomous agent action) the nearest valid coding is used and the AI meaning is carried in the report layer.
- **Ranking.** By **observed** severity (`report.observed_severity`), then **potential** severity (`report.potential_severity`), then the ID number (`ranking_table`; methodology §9.3) — a report-specific ordinal rubric (Critical > High > Medium > Low > Negligible), **not** CVSS, the ChatGPT report's AIRIS, or the CC report's blended tier. Vulnerability-discovery / coordinated-disclosure PoC items sit at Negligible/Low observed and High/Critical potential.
- **Non-software-security rows.** Five MIT/VCDB register items are `security_incident = False positive` (privacy/likeness/governance harms, not asset compromises); ten conventional VCDB breaches with no AI component are flagged as such. Both are retained for register completeness, each with an AI-involvement note.
- **CVE validation (2026-08-26).** Every CVE ID in the original records was resolved against CVE.org/NVD and checked against the incident description; CISA KEV, the GitHub Advisory Database and each incident's primary sources were searched for omitted CVEs. The per-incident **Validated CVEs** line (and the `validated_cve` / `validated_cve_details` attributes in the JSON, `validated_cve` column in the CSV) carries the corrected list, grouped by relation (*exploited*, *self-malicious-release*, *exploited-unconfirmed*, *attempted*, *toolkit*, *self-vulnerability*, *discovered*, *related*), with removed IDs and their reasons. Titles and summaries keep every CVE ID as cited, so a title may still cite an ID that the validation line removes or re-attributes; where a record was split, its text about the split-off event moved to the new record (methodology §6.4). The VERIS `action.hacking.cve` / `action.malware.cve` fields in the JSON hold exactly the validated *exploited* CVEs.
